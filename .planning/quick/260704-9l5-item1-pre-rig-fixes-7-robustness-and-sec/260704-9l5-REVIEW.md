## Summary

I traced every high-risk path called out in the brief: the Task-7 auth gate (constant-time compare,
route coverage, CSRF, secret leakage), the Task-2 receiver fault isolation + tick-loop supervisor,
the Task-1 latency-warmup disjointness, and the Task-3/4/5/6 env/logging/health/preflight wiring.

**No CRITICAL or blocker-tier defect was found, and I am stating that explicitly rather than
manufacturing one.** The security gate is sound for its stated threat model, the constant-time
compare is correct and cannot throw, all three mutating routes (`/score`, `/run`, `/command`) are
POST-only and therefore fully covered by the method-based gate, the secret does not leak into
`/status`, logs, or error bodies, the latency warmup tracker is genuinely a distinct `YOLO()`
instance (disjoint model + callbacks), `DirectorStatus`'s new field did not break any positional
caller (all constructions use keyword args), and `configure_logging` is idempotent (no stacked file
sinks). The residual findings below are two real robustness gaps (WARNING) and five
lower-value notes (INFO) — none violate "nessun crash ammesso," but two partially undercut the
stated intent of the fixes they belong to.

## Verified-clean (adversarial checks that passed)

- **Constant-time Bearer compare** (`app.py:332`): `hmac.compare_digest(bytes, bytes)`; a non-ASCII
  secret encodes cleanly, an omitted header becomes `""` → compares False → 401. No bypass, no throw.
- **Route coverage** (`app.py:327`): gate keys on `request.method != "POST"`; the only mutating
  routes are `@app.post` (`/score` 382, `/run` 429, `/command` 452). No PUT/DELETE/GET writer exists,
  so there is no method-spoofing bypass.
- **Secret leakage**: absent from `/status` payload (only `live_cam/reason/obs_connected/alive`),
  absent from every `logger.*` call (the `__main__` warning names the *env var*, never a value),
  absent from `abort(401/403)` bodies. Inlined only via `| tojson` into the two console pages (safe
  JS string literal — a secret containing quotes/`</script>` cannot break out or self-DoS).
- **Task-1 disjointness** (`test_latency.py:307` + `detector.py:252/262/274`): each
  `PerCameraTracker` builds its own `YOLO(...)`; `_warm` is a separate object, so its serial
  `.track()` `on_predict_start` registration cannot pollute the loop trackers' batched feats hook.
- **`configure_logging` idempotency** (`logging.py`): `_FILE_SINK_ID` guard means a second call with
  the same/absent `log_dir` adds no duplicate file sink; `force` correctly re-arms both sinks.
- **`DirectorStatus` field insertion** (`records.py:154`): inserted between `reason` and `alive`,
  but every construction in `src/` and `tests/` uses keyword args (`alive=...`), so no positional
  caller silently binds `alive` into `obs_connected`. `read_status` defaults it True (no false alarm
  on a legacy `status.json`).
- **Task-3 port/password parse** (`runtime.py`): non-int `SEGUGIO_OBS_PORT` coasts to 4455 with a
  warning; empty-string password → `None`. No crash.

## Warnings

### WR-01: Receiver setup region is outside the fault-isolation try/except — a persistent setup fault respawns forever with unthrottled, un-captured stderr tracebacks

**File:** `src/segugio/ndi/ndi_source.py:283-310` (setup) + `src/segugio/orchestrator/loop.py:686-687` (supervisor)
**Issue:** Task-2 wraps only the per-iteration BODY (`_run_receiver`, lines 333-392). The receiver
*setup* in `_receiver_loop` — `_prefer_system_ndi_runtime()`, `import cv2`, `from cyndilib... import`,
`Finder()`, `finder.open()`, `_resolve_source`, `receiver.set_source` (lines 283-303) — runs BEFORE
the guarded loop and is NOT isolated. If any of those raises persistently (the exact NDI-runtime
pairing gotcha called out in MEMORY.md, or a cyndilib import/`Finder.open()` failure), the thread
dies immediately. The new tick-loop supervisor (`loop.py:686`, every ~1s) then calls
`source.start()`, which respawns the dead thread, which dies again in setup — a ~1 Hz respawn loop.
Each death is an *uncaught* exception routed to `threading.excepthook`, printing a full traceback to
`sys.stderr` every second. That spam is (a) not throttled like the body's `_RECEIVER_FAULT_LOG_EVERY`
path, and (b) NOT captured by the new loguru rotating file sink (Fix #4 only captures `logger.*`
calls, not raw stderr) — so the very post-mortem log Fix #4 exists to produce will be missing the
dominant failure. This does not crash the process and the director correctly degrades to SAFE, so it
is not a blocker — but it defeats the "throttled coast + diagnosable log" intent of both Fix #2 and
Fix #4 on exactly the failure class (NDI runtime pairing) the team has already been bitten by.
**Fix:** Move the setup into the same isolation, e.g. wrap the `finder/receiver` construction +
`_resolve_source` in a try/except that logs through `logger` (throttled) and coasts one poll
interval, OR restructure so `_run_receiver`'s `while not self._stop.is_set()` guard also covers a
failed setup (re-attempt setup inside the loop). At minimum, install a `threading.excepthook` that
routes thread-death tracebacks through `logger.error` so they land in `segugio.log`.

### WR-02: Connected-path fault retries at a 2 ms cadence — ~500 exceptions/sec/camera on a persistent fault

**File:** `src/segugio/ndi/ndi_source.py:392`
**Issue:** The new body `except` handler ends with `time.sleep(_RECEIVER_POLL_INTERVAL_S)` where
`_RECEIVER_POLL_INTERVAL_S = 0.002` (line 82). On a *persistent* connected-path fault (e.g.
`capture_video()` or the reshape throwing every iteration), the loop re-enters the try, throws, and
retries ~500×/sec per camera — constructing/formatting an exception each time. It is not a true
CPU-pinning busy-spin (the 2 ms sleep yields the GIL, satisfying the brief's "must sleep between
retries" bar), and the `_RECEIVER_FAULT_LOG_EVERY = 150` throttle keeps logging to ~3 lines/sec, so
this is a WARNING, not a blocker. But 2 ms is the *healthy-poll* cadence, not a *fault* backoff — the
disconnected branch already coasts at 50 ms (`_RECEIVER_DISCONNECTED_SLEEP_S`) for the same reason.
With 3–4 cameras all faulting, this is ~2000 exceptions/sec of avoidable churn on the box running the
<300 ms AI loop.
**Fix:** Back off on a fault streak — sleep the longer disconnected interval once `fault_streak > 1`:
```python
except Exception as exc:  # noqa: BLE001
    fault_streak += 1
    if fault_streak == 1 or fault_streak % _RECEIVER_FAULT_LOG_EVERY == 0:
        logger.warning(...)
    time.sleep(_RECEIVER_DISCONNECTED_SLEEP_S if fault_streak > 1 else _RECEIVER_POLL_INTERVAL_S)
```

## Info

### IN-01: `obs_connected` health is only refreshed when a cut is attempted — stale "connesso" during static-scene stretches

**File:** `src/segugio/orchestrator/loop.py:509,560` + `src/segugio/obs/obsws_controller.py:145`
**Issue:** `connected` = `_connected and _consec_failures == 0`, and `_consec_failures` only moves
inside `_safe_call`, i.e. when `cut()`/`set_pip()` actually runs. `_apply` calls `cut()` every tick,
but if OBS drops while the FSM is parked on one camera and the director keeps re-cutting the same
scene, the counter does update — however if no OBS op runs at all (e.g. a long steady hold where the
apply path is skipped), the badge can read "OBS: connesso" while OBS is down until the next real op.
It is a reachability *heuristic inferred from cut attempts*, not a live ping. Acceptable for v1 but
worth documenting so the operator does not over-trust a green badge.
**Fix:** Optionally issue a cheap periodic OBS keepalive (e.g. `get_version`) through `_safe_call`
every N ticks so `connected` reflects reachability even with a static program scene.

### IN-02: The Bearer secret is a CSRF token, not a network-access credential — it is served in cleartext by the ungated GET `/`

**File:** `src/segugio/ui/app.py:345-361` + `templates/console.html:317`
**Issue:** By design, reads stay open (`T-9l5-03 accept`) and the secret is inlined into `/` and
`/score-entry` so the console can attach it to its own same-origin POSTs. Consequence: anyone who can
reach the console over the network can `GET /`, scrape `window.__CONSOLE_SECRET`, and POST. The
secret therefore provides *CSRF* protection (a cross-origin attacker page cannot read the opaque
response, and cannot set an `Authorization` header on a simple/forged request without a blocked CORS
preflight) but provides *zero* protection against a hostile actor already on the LAN. This is
consistent with the accepted trusted-dedicated-WiFi posture — flagged only so it is not mistaken for
an access-control boundary.
**Fix:** None required under the stated threat model. If LAN-level access control is ever needed,
the secret must not be embedded in an ungated GET (move to a login flow / gate the read routes too).

### IN-03: CSRF Origin check fail-opens on absent Origin; Referer-only cross-site POST is not checked

**File:** `src/segugio/ui/app.py:337-342`
**Issue:** The Origin check runs only `if origin is not None`. A cross-site POST that omits `Origin`
(or sends only `Referer`) skips the check. This is safe *because* the Bearer secret is the primary
CSRF control (and cannot be forged cross-origin), so the Origin check is defense-in-depth — but the
fail-open is worth recording. `urlparse(origin).netloc != request.host` is otherwise robust
(includes port; browsers normalize host case; `Origin: null` → `""` → 403).
**Fix:** None strictly needed. If hardening: treat a present-but-mismatched `Referer` as a reject too,
and keep the Bearer gate as the authority.

### IN-04: `SEGUGIO_OBS_PORT` accepts nonsensical-but-integer values without warning

**File:** `src/segugio/orchestrator/runtime.py:74-83`
**Issue:** Only a non-integer port is caught and defaulted. `SEGUGIO_OBS_PORT=0` or `=-1` parses via
`int()` and is passed through to the controller, which will simply fail to connect (coasting to a
down-OBS state). Not a crash, just a silent misconfiguration with no operator signal.
**Fix:** Range-check `1 <= port <= 65535` and fall back to the default with the same warning path.

### IN-05: `preflight` adds a synchronous ~2 s startup stall and opens a second Finder concurrent with the receiver-thread Finders

**File:** `src/segugio/ndi/ndi_source.py:439-503` + `src/segugio/orchestrator/loop.py:670-672`
**Issue:** `run()` calls `source.start()` (which spawns per-camera receiver threads, each opening its
own `Finder`) and then `source.preflight()` with `wait_s=2.0`, which opens *another* `Finder`, sleeps
2 s, reads names, and closes it. This delays `obs.connect` and the first tick by ~2 s and briefly
runs an extra Finder alongside the receivers' Finders. Best-effort and never-raises are correct; the
stall is acceptable at startup. Noted because the extra concurrent Finder is exactly the class of
cyndilib interaction that has been fragile on this rig (verify on hardware).
**Fix:** Optional — run preflight *before* `source.start()` (reuse its finder), or drop `wait_s` to
the minimum discovery latency the rig needs.
